## Key Decisions

- Migrated directly from the live Web Awesome implementation instead of reconstructing or reverting to a pre-Web-Awesome tree. This protected unrelated work and avoided validating an artificial intermediate state.
- Removed preview infrastructure permanently rather than leaving dormant routes or a replacement harness. Browser verification now uses disposable external fixtures generated from production components.
- Used a pinned standalone Tailwind binary instead of npm, PostCSS, a bundler, or a global executable. This keeps the Go application self-contained while making CSS generation reproducible.
- Trusted a Tailwind executable only when both its exact version and pinned platform checksum matched. Version output alone cannot establish binary provenance.
- Installed verified downloads atomically so a failed or tampered download cannot replace a known working executable.
- Kept application styling utility-only. Existing self-hosted font declarations are the sole handwritten CSS exception, preventing a second component-CSS system from reappearing.
- Adapted the closest relevant blocks from the local Tailwind Plus source without modifying, vendoring, or redistributing complete licensed source files.
- Loaded Tailwind Plus Elements from the approved versioned major CDN module URL and limited markup to Elements tags supported by that package.
- Used inline templ Heroicons to avoid icon CDNs and runtime icon libraries while keeping accessibility attributes explicit and server-rendered.
- Built wrappers around semantic HTML, caller-provided IDs, valid ARIA relationships, successful native form controls, and progressive enhancement. Elements behavior augments rather than replaces server contracts.
- Treated mobile navigation, dialog focus management, Escape handling, and form submission semantics as required behavior, not visual polish.
- Used Go tests for server-visible contracts and local Chrome CDP for browser-only interaction behavior. The built-in browser was not used in final verification.

- Fixed partial-install risk by staging, verifying, and atomically replacing the Tailwind binary while preserving the previous executable on failure.

- Fixed dialog behavior so opening moves focus inside, Escape closes it, and closing restores focus to the trigger.

- Removed duplicate IDs and strengthened tests around caller-provided identifiers, trigger/panel relationships, labels, tabs, and active state.

- Hardened fixture output-path validation so tests write only to an absolute path below the approved temporary root and never into the repository.
- Fixed fixture asset references to include exactly one copied `/output.css`, one copied `/theme.js`, and one exact Elements CDN module script.
- Expanded the fixture to call every production wrapper and production icon helper instead of duplicating simplified test-only component markup.
- Added missing interaction coverage for all eight themes, dialog focus and restoration, dropdown actions, select submission, combobox selection, tabs, disclosure, popover, command palette, tooltip, and toast behavior.
- Added missing component, page, handler, asset, theme, generation, reproducibility, allowlist, and cleanup tests that had left master DoD criteria unproven.

## Watch Out For

- A Tailwind upgrade requires coordinated changes to the pinned version, every platform checksum, setup tests, runner validation, generated CSS, and reproducibility expectations.
- Never weaken binary trust to version output alone. Reuse requires both the approved checksum and exact version.
- Keep `setup.sh` source-safe; top-level provisioning outside its guarded `main` path would make focused tests mutate developer environments.
- Preserve both first-exit and simultaneous-exit branches in `run.sh`; simplifying process cleanup can reintroduce leaked processes or lost failure statuses.
- Do not restore preview routes, flags, templates, scripts, package files, or a committed browser harness.
- Do not add custom component or page CSS. New styling belongs in Tailwind utilities; only approved Tailwind/theme constructs and existing `@font-face` declarations belong in `input.css`.
- Use only custom elements supported by the pinned Elements major version. Similar-looking tag names are not interchangeable.
- Elements-enhanced controls must still preserve native successful form controls, names, submitted values, labels, IDs, and server-rendered fallbacks.
- Dialog changes must retain focus entry, Escape close, focus restoration, `role="dialog"`, and `aria-modal="true"`.
- HTMX endpoints that promise fragments must never return or swap a full page; preserve stable fragment IDs and polling attributes.
- Caller-provided IDs must remain unique across repeated wrappers. Tests should cover complete rendered pages, not only wrappers in isolation.
- The temporary browser fixture must remain outside the repository, use production wrappers, copy production assets, bind to loopback, and always clean up Chrome, its profile, the server, and fixture files.
- Keep browser verification independent of the built-in browser. Final verification used locally installed Google Chrome headless via CDP.
- Do not modify, vendor, or redistribute `/Users/divy/Downloads/tailwind_plus`; adapt only the necessary patterns and retain source-safety verification.
- Preserve all eight theme names and their persistence semantics. Changing a token name, fallback, or remembered mode can break both pre-paint theme application and HTMX resynchronization.
